# 딥리서치 내부고객 검수 (2026-09-19 사장님 지시)

## 최종 실측의 기준
- **딥리서치 과제의 최종 합격은 기술이 아니라 내부고객인 마야와 핏이 과정과 결과물에 만족할 때다.** (사장님 지시, 2026-09-19)
- 기술 동작(발주가 돌아가는지, 검증 도구가 판정을 내는지, 오류가 표시되는지)은 탐이 본다. 이 문서는 그 위에서 마야와 핏이 실제 업무로 써 보고 평가하는 절차다.
- 구성과 절차 정본: `docs/딥리서치_파이프라인.md`. 검증 도구: 헤르메스 `scripts/verify_claims.py`.

## 시범 업무 (고객이 실제로 필요한 일 1건씩)
| 고객 | 시범 업무 | 기술 확인은 탐 |
|---|---|---|
| 마야 | 발행 전 사실 검증: 진행 중인 글(628번 후보)의 핵심 주장을 출처와 대조 (`reports/maya-628-claims.md`에 주장 목록 있음) | 발주 → 헤르메스 수집 → `verify_claims.py` → 판정 표 |
| 핏 | 본인 업무에서 지금 궁금한 것 1건(예: ComfyUI/LTX 로딩 설정, 모델 파일명 확인). 핏이 직접 고른다 | 발주 → 헤르메스 조사 → 보고서 |

- 제미나이 3.6-flash 무료 한도(키당 하루 20회) 때문에 **검증 단계 실행은 한도가 초기화된 뒤(2026-09-20 이후)** 로 잡는다. 한도가 없으면 도구는 `error`를 표시하고 판정하지 않는다.
- 고객은 발주부터 결과 수령까지 사장님께 복사·붙여넣기를 부탁하지 않는다. 우편함과 `tasks/pending/`을 쓴다.

## 평가서 (고객이 우편함으로 탐과 사장님에게 회신)
받는이: 탐, 사장님. 제목 예시 `딥리서치 평가 마야`. 형식은 자유, 아래 6개에 답한다.
1. 발주가 쉬웠나 (1~5점, 어디서 막혔나)
2. 결과를 그대로 쓸 수 있었나 (1~5점, 고쳐야 했던 부분)
3. 출처와 검증 표시를 믿을 만했나 (1~5점, 의심 간 곳)
4. 기다린 시간(발주 후 결과까지)이 괜찮았나
5. 불편했던 점 한 줄
6. 다음에도 쓰겠나 (예 / 아니오 / 조건부: 조건)

## 합격 기준 (초안, 사장님이 확정)
- 마야와 핏 둘 다 6번이 "예" 또는 "조건부(조건이 해결 가능)".
- 1~3번 평균이 각각 3.5점 이상.
- 미달이면 지적된 지점을 고쳐서 같은 시범 업무를 한 번 더 한다(2회차). 2회차도 미달이면 파이프라인 구성 자체를 재검토한다.

## 진행 상태
| 항목 | 상태 |
|---|---|
| 시범 업무 안내 우편(마야, 핏) | 발송함(2026-09-19 밤) |
| 마야 평가 회신 | 대기 |
| 핏 평가 회신 | 대기 (핏 세션은 승인 카드 확인 후 사장님이 여는 대로) |
| 탐의 기술 확인 메모 | 시범 업무 실행 후 작성 |
