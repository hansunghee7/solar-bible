# 타미(헤르메스)를 클라우드 탐의 손발로 고도화하는 백로그 (2026-10-08 탐 클라우드, 사장님 지시)

목적: 클라우드 탐이 못 하는 일을 타미가 대신하고, 지시 → 중간 피드백 → 완료 피드백의 리드타임을 최소화한다. 사람이 중간에서 전달하거나 물어보는 일을 없앤다.
이 문서는 초안이다. 숫자는 표시한 것만 실측이고 나머지는 가설이다. 알림 채널의 방식과 설치 절차는 `docs/알림_채널_표준_GitHub봇댓글.md`에 있다.

## 1. 지금 측정된 리드타임 (표본이 적다)
- L1 지시 → 타미 착수: 1건 실측 약 30초(지시서 push 02:53:56Z, 타미 처리 02:54:27Z). 폴러가 빠르게 집어 갔다.
- L2 중간 피드백: 구조가 없다(지시서는 끝날 때 한 번만 회신).
- L3 완료 → 클라우드 탐 인지: 시험 2 이전에는 구조가 없어서 예약 폴링(12~20분 간격)과 사람의 질문에 의존했다. 시험 2에서 푸시 경로가 약 12초로 측정됐다(B1).
- L4 인지 → 다음 지시: 클라우드 탐의 턴이 돌 때만 가능(알림으로 깨어나면 바로 가능).

## 2. 클라우드 탐이 못 하는 것 (타미가 손발이 될 대상)
- 외부 서비스 호출: tally.so가 막혀 폼 제출·삭제·시험 불가, 제미나이·Vertex 호출, 비티·덱스 호출.
- 사장님 PC 안의 일: 텔레그램 발송(봇 토큰), 로컬 우편함 읽기·쓰기, 로컬 파일, 로컬 LLM·GPU, SSH.
- 로그인 상태가 필요한 화면 조작, 비밀값이 필요한 DB 실행(승인 후).
- 다른 세션 깨우기(권한 오류): 로컬 세션(핏)에 직접 못 알린다.

## 3. 백로그 (우선순위순, 각 항목 = 방법 / 끝났다는 증거)

### P0. 리드타임 줄이기
- **B1 완료·수신 알림을 클라우드 탐에게 푸시. [시험 통과 2026-10-08]** 타미가 수신 문서·완료 문서·결과 문서를 main에 올리면 워크플로(`.github/workflows/notify-inbox.yml`)가 "[수신함]" PR(solar-bible#2)에 봇 댓글을 달고, 클라우드 탐이 그 PR을 구독해 알림으로 받는다. 결과: 시험 1(사장님 계정이 단 댓글)은 11분 안에 알림이 오지 않았고, 시험 2(github-actions 봇이 단 댓글)는 푸시 04:20:53Z 후 약 12초(알림 도착 04:21:05Z)에 도착했다. 표본은 각 1건이라 반복 확인이 필요하다. 한계: 세션이 작업 중일 때 도착한 알림은 그 턴이 끝나야 읽혀 지연이 더 길어질 수 있고, 쉬는 세션에서의 깨우기 지연은 별도로 재야 한다.
- **B2 중간 피드백 표준.** 타미 지시서 템플릿에 "단계마다 `notify/<이름>-progress.md`에 한 줄 push"를 넣고, 같은 워크플로가 알림으로 올린다. 증거: 3단계 작업에서 단계마다 알림 3건.
- **B3 지시 → 착수 시간 실측.** 표본 10건으로 L1 분포(중앙값, 최대)를 잰다. 느리면 폴 주기를 줄이거나 푸시 방식(원격 변경 감지 후 즉시 실행)을 검토한다. 증거: 중앙값 60초 이하.
- **B4 새 클라우드 탐 세션이 시작되면 수신함 PR을 자동 구독.** 구독은 세션 단위라 새 세션은 알림을 못 받는다. 증거: 새 세션 첫 턴에서 구독 확인.
- **B15 로컬 세션에서 같은 구독이 되는지 시험.** 사장님 결정(10/8): 클라우드 탐이 로컬 탐으로 전환해도 이 채널을 계속 쓴다. 로컬 세션에서 수신함 PR을 구독하고 시험 파일을 올려 도착 여부와 시간을 잰다. 안 되면 B13(우편함 감시)으로 대체. 증거: 로컬 세션에서 봇 댓글 알림 도착 1건 이상.

### P1. 손발 카드 라이브러리 (한 줄 명령으로 위임 가능한 일)
- **B5 폼 시험 제출 카드.** 타미가 브라우저 자동화로 폼을 제출하고 T0를 기록한다. 푸시 실험을 사람 없이 반복하게 해 주는 핵심 항목이다. 증거: 같은 폼에 10건 자동 제출, 도착 지연 측정.
- **B6 시험 응답 정리 카드.** 테스트 제출 삭제(폼 서비스 API 또는 화면 조작, 키는 금고 참조만).
- **B7 텔레그램 발송 카드.** 기존 `tg_boss.py`를 한 줄 카드로 고정(글·사진·파일). 증거: 지시 후 2분 안에 발송 성공.
- **B8 제미나이 리서치 + 비티·덱스 검토 카드.** 오늘 만든 스크립트를 표준 카드로 편입(질문 목록만 바꿔 쓰기). 증거: 한 번에 세 결과 파일.
- **B9 DB 실행 카드(승인 기록 포함).** 승인된 SQL만 실행하고 select로 확인(예: 작업기 장부 표).
- **B10 로컬 LLM 요약 카드.** 큰 로그·문서를 로컬 모델로 먼저 요약해 토큰을 아낀다.
- **B16 지투시그마 전용 수신함 내부 시험.** 사장님 결정(10/8): 이 채널을 지투시그마 에이전트와의 기본 소통 채널로 쓴다. 고객 저장소 설치는 고객 동의와 사장님 승인이 먼저라, 먼저 우리 비공개 저장소에서 지투시그마 전용 수신함으로 내부 시험한다. 증거: 비공개 저장소에서 봇 댓글 알림 도착. 선행 조건 상세는 알림 채널 표준 4절.

### P2. 신뢰성과 확장
- **B11 하트비트·실패 알림.** 폴러가 멈추면 푸시로 알린다(기존 감시 연결). 증거: 폴러 중지 시 5분 안에 알림.
- **B12 결과 자동 검증.** 완료 문서가 성공 기준을 만족하는지 스크립트로 확인(인용 원문 대조 등 기존 도구 활용). 증거: 성공 기준 위반 시 자동 "실패" 표시.
- **B13 로컬 세션 깨우기(핏).** 로컬 세션 시작 훅이 우편함 감시를 자동으로 띄운다. 증거: 새 우편이 오면 이벤트로 도착.
- **B14 폼 응답 수신 허브.** 폼 웹훅 → 서버 함수 → 같은 수신함 통로(봇 작성자 필요). 폼 서비스가 보내는 형식이 GitHub과 달라 변환 함수가 필요하다. 설계는 비티·덱스 검토(2026-10-08 의뢰) 뒤 확정.

## 4. 지금 하지 않을 것
- 범용 이벤트 버스, 대시보드: 알림 소스가 3개 이상으로 늘기 전에는 과하다.
- 별도 봇 계정 신설: 계정 생성은 에이전트 금지 영역이다. 워크플로 봇(github-actions)으로 먼저 시험했고 통과했다.
- 타미에게 상시 로그인 브라우저를 맡기기: 자격증명 노출 위험. 필요한 카드(B5, B6)부터 좁게 시작한다.
- 고객 저장소에 승인 없이 설치하기.

## 5. 판단 기준과 다음 신호
- 목표: L1 ≤ 60초, L2 단계마다 ≤ 60초, L3 ≤ 120초(95번째 백분위).
- 다음 단계로 넘어갈 신호: 위임 카드가 주 5건 이상 쌓임 / 외부 고객 대상 알림이 필요해짐. (B1의 시험 통과 신호는 달성됨, 반복 표본 확인은 남음)
