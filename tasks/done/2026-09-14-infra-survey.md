## 발주: 탐 → 신솔라

status: QUEUED
받는 이: 신솔라 (구PC 항목은 조사 가능하면 직접, 안 되면 사장님께 물어볼
목록으로 남겨도 됨)

## 배경

탐이 앞으로 신/구솔라에게 작업을 적재적소로 배분하려면(예: GPU 필요한
작업은 신PC, 가벼운 상시 작업은 구PC) 인프라 실태를 알아야 한다. 지금은
전혀 모르는 상태다.

## 조사 항목

1. **신PC 사양**: CPU, RAM 용량, GPU(RTX 4090으로 알고 있음, 확인),
   SSD 용량, HDD 용량(있다면). 각각 실제 값(예: "1TB NVMe SSD + 2TB HDD"
   처럼)으로.
2. **구PC 사양**: 위와 동일 항목. 신솔라가 구PC에 원격으로 접근 가능하면
   직접 조사, 안 되면 "확인 불가, 사장님 확인 필요"로 남긴다.
3. **텔레그램 연동 상황**: 신솔라·구솔라 각각 봇이 실제로 연결돼 있는지,
   어느 채널/그룹인지(봇 토큰 값 자체는 절대 적지 마라, 연동 여부만).
   §10에 "비밀값 출력 금지"가 이미 있다 - 그대로 지킨다.
4. **신솔라 ↔ 구솔라 상호 통신 방식**: 지금 솔라바이블엔 "신솔라가
   내부적으로 위임한다"고만 되어 있고 실제 메커니즘이 안 적혀 있다.
   실제로 어떻게 서로에게 지시를 전달하는가(파일 공유? 네트워크 호출?
   사람이 껴야 하는 수동 방식뿐인가?)를 사실대로 적는다. "이렇게
   될 것이다"가 아니라 실제로 확인된 것만.
5. **웨이크업 가능 여부**: 신PC가 구PC를(또는 그 반대로) 원격으로
   켤 수 있는 수단(Wake-on-LAN 등)이 실제로 설정돼 있는지 예/아니오로.
   **주의: 이 저장소는 공개(public)다. MAC 주소·IP·비밀번호 같은 구체적
   네트워크 식별자는 여기 절대 적지 마라 - "설정됨/안 됨"까지만 적고,
   구체적인 값은 로컬 파일에만 남긴다.**

## 완료 기준

위 5개 항목을 `tasks/done/`으로 옮긴 이 파일 안에 사실 그대로 적는다.
모르면 "모른다"고 적는다(추측 금지, 솔라바이블 §10). 구PC 항목 중
조사 못 한 게 있으면 "사장님 확인 필요" 목록으로 따로 정리한다.

## 조사 결과

- CPU: AMD64 Family 25 Model 97 Stepping 2 AuthenticAMD, ~3701MHz (1소켓·1코어 보고; Zen 5 계열로 보임, 실제 물리 코어는 추가 확인 필요)

- GPU: NVIDIA GeForce RTX 4090, VRAM 24564 MiB(약 24GB), 드라이버 591.86
- 저장장치:
  - C:/: 총 999.10GB / 사용 885.71GB / 여유 113.38GB → 약 1TB NVMe SSD (시스템·프로그램)
  - D:/: 총 8001.55GB / 사용 8.29GB / 여유 7993.26GB → 약 8TB 저장용 드라이브(HDD일 가능성 높음, 유형은 미확정)
- OS: Windows 11 Home, 빌드 10.0.26200

- 비고: Python 3.14.7, Hermes Agent 실행 중. 이 세션의 Hermes 환경은 API Server 127.0.0.1:8642, MCP Adapter 127.0.0.1:8765/mcp 등.

### 2. 구PC 사양

- 직접 조사 불가. 이 세션 호스트에서 구PC 접속 수단(SSH 키/계정, WinRM 등)이 사전 구성돼 있는지 확인되지 않았음. Tailscale 상태에 구PC로 보이는 윈도우 노드 하나가 idle 상태로 떠 있으나, 이 세션에서 해당 노드로의 접근 자격을 알지 못해 실제 사양 조회가 안 됨.
- **사장님 확인 필요 목록** (구PC 직접 접근 가능해지면 확인):
  - 구PC가 맞는지(추정 노드와 실제 구PC 동일 여부) 확인
  - CPU 모델·코어 수, RAM 용량, GPU 모델·VRAM(있다면), SSD/HDD 용량·유형, OS 버전
  - 구PC에 SSH/WinRM 등 원격 접근 수단이 설정돼 있는지, 그 계정·키 정보(별도 안전한 채널로 전달)
- 주의: 이 저장소(공개)에 MAC 주소/IP/비밀번호 등 구체적 식별자는 기재하지 않음. "설정됨/안 됨"까지만.

### 3. 텔레그램 연동 상황

- 신솔라: 이 세션에서 Hermes Agent 실행 중. 텔레그램 게이트웨이 연동 여부는 게이트웨이 상태 메타 정보로 확인 가능하나, 이 자리에서는 게이트웨이 로그 직접 열람 및 getUpdates 수동 호출을 하지 않음(이전 설정된 규칙). 봇 토큰 값 등 비밀값은 기재하지 않음. 연동 여부 자체는 게이트웨이 상태 명령으로 확인 가능함(필요 시 별도 확인).
- 구솔라: 구PC(desktop-202ap4o 추정)에서 Hermes Agent가 실행 중일 가능성이 있으나, 구PC 사양·연결 미확인이므로 구솔라 텔레그램 봇 연동 여부도 이 자리에서 단정 불가 → "구PC 접근 가능해지면 실제 확인, 현재는 확정 불가"로 남김.
- 준수: §10 비밀값 출력 금지 적용. 연동 여부만 기재.

### 4. 신솔라 ↔ 구솔라 상호 통신 방식 (실제로 확인된 것만)

- 네트워크 도달성: 신PC와 구PC 추정 노드가 Tailscale로 서로 연결되어 있음. 즉 두 머신 간 네트워크 레벨 연결은 실제 확인됨(연결됨).
- 작업 발주·처리 채널: 이 저장소(GitHub, public)의 `tasks/pending/` → pull → 처리 → `tasks/done/` → push 흐름이 실제로 사용되고 있음(이 파일 처리가 그 예). 이게 신↔구솔라 간 작업 전달 메커니즘 중 하나로 실제 작동 중.
- 구PC 측 Hermes Worker가 직접 조작 불가한 경우, 구PC 측이 저장소를 fetch → 실행 → 결과 push하는 중위 전달 방식이 이전 확인된/의도된 방식.
- Hermes 간 브리지 구현 참고: "Hermes 간 업무 브리지를 GitHub 저장소로 구현할 때 구조는 README + tasks/incoming/completed/failed + reports로 고정한다"는 정리 존재(이번 작업은 pending/done 구조를 쓰는 별도 흐름으로 보임).
- 미확인: "신솔라가 내부적으로 위임한다"는 표현의 구체적 명령 전달 경로(실시간 명령 전송인지, 저장소 폴링인지 등)가 이 자리에서 모두 확정된 것은 아님. 구PC 측 Hermes 설정/실행 방식 확인이 추가로 필요할 수 있음 → "추가 확인 필요"로 남김.

### 5. 웨이크업 가능 여부 (Wake-on-LAN 등)

- 구PC를 신PC에서 원격으로 켤 수 있는지(WoL, BIOS/OS 전원 설정, Tailscale WoL 지원 등)는 구PC 전원·네트워크 설정 확인이 필요. 구PC 접근 불가이므로 현재 이 세션에서 확인 불가 → "설정 여부 확인 불가, 사장님 확인 필요".
- 신PC 자체의 WoL 수신 설정 여부는 이 세션 호스트 NIC 전원 관리로 확인 가능할 수 있으나, 구PC를 깨우는 능력과는 별개. 구PC 쪽 준비가 있어야 의미가 있음.
