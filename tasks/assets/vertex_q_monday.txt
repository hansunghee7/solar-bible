당신은 소프트웨어 회사의 보안·운영 검토자다. 아래 두 문서 초안을 검토해 주세요. 회사는 "대표가 AI 에이전트로 서비스를 직접 고쳐 보고 운영에 반영하는 파일럿"을 시작하려 한다. 방침은 "에이전트가 검토용 PR까지 만들고 병합과 배포는 사람이 한다"이다.

## 문서 A: 환경 확인 체크리스트
1. 브랜치 보호: main 직접 push 금지, 병합은 PR과 사람 승인 1명 이상. 에이전트 계정은 승인자가 될 수 없고, 에이전트 PR에는 자동 병합을 켜지 않는다. 확인할 것: 현재 설정, 필수 검사(CI) 유무.
2. 계정과 토큰: 에이전트 전용 계정을 사람과 분리하고 이름으로 누가 했는지 남긴다. 처음에는 읽기 전용 토큰, 쓰기는 PR용 작업 브랜치만. 확인할 것: 토큰 만료일, 회수 방법, 비밀 저장소 보관.
3. 키 분리: 개발·스테이징·운영 키를 분리하고 에이전트에게 운영 키를 주지 않는다. 확인할 것: 환경별 분리 여부, 에이전트가 읽는 설정 파일에 키가 있는지.
4. 스테이징 접근과 시연 범위: 서버 스테이징 접속은 아직 닫혀 있다. 처음에는 웹 미리보기 연결부터. 시연 범위는 작은 문구·UI 수정 하나.
5. 승인·중단·복구: PR 승인은 대표(결과 확인)와 개발팀(기술 검토). 문제가 생기면 승인자와 개발팀 담당이 중단, 복구는 PR 되돌리기(revert). 확인할 것: 중단 권한자 두 명, 복구 연락 방법.
6. 기록: 에이전트 이름이 붙은 커밋과 PR, PR 설명에 변경 이유와 테스트 결과, 보고 채널에도 남긴다.
7. 시연 통과 기준: ① 대표가 스테이징에서 수정된 화면을 직접 확인 ② 변경 내용과 테스트 결과가 담긴 검토용 PR이 있음.

## 문서 B: AI에 넣어도 되는 데이터 규칙
기준: 회사 Team 계정으로만 쓴다.
- 넣어도 된다: 공개 문서, 제품 UX 지침, 스토리·완료기준·회의록(허용 범위), 읽기 전용으로 열어 준 소스 코드(키 제거 후), 가짜·합성 데이터.
- 가려서 넣는다: 설정·환경 파일(키와 주소 제거), 고객 인터뷰는 요약본만, 로그와 화면 캡처(이름·연락처 마스킹).
- 넣으면 안 된다: 고객 통화 녹음·전사·연락처 등 개인정보, 운영 DB, 결제·계좌 정보, 키·토큰·비밀번호, 재무·인사·투자 자료.
- AI 서비스 설정(확인 필요): 입력 내용의 저장·학습 사용 설정과 보존 기간을 확인해 기록한다.
- 새 종류의 데이터는 대표 승인 후 규칙에 한 줄 추가. 판단 한 줄: "밖으로 새면 고객이나 회사에 피해가 가는가?"
