## 발주: 탐 → 구솔라

status: QUEUED

받는 이: 구솔라 — 이 발주부터 먼저 처리해라(텔레그램 발주보다 먼저:
이게 돼야 앞으로 발주를 매번 사람이 깨워서 전달 안 해도 된다)

## 배경

지금까지 구솔라는 자동 폴링이 없어서, 큐에 새 작업이 생겨도 사장님이
매번 터미널에 직접 지시를 넣어야 처리됐다(2026-09-15 오늘 실제로 여러
번 그랬다). 신솔라는 이미 `solar-bible-tasks-poller`라는 이름의 Hermes
cron 잡이 3분 주기로 자동 처리하고 있다. 사장님이 오늘 구솔라도 같은
방식으로 자동화하기로 결정했다(solar-bible.md §14 반영 완료).

## 작업

1. `hermes cron status`로 이 PC(구솔라)에 이미 비슷한 잡이 있는지 먼저
   확인한다. 있으면 그걸 손보고, 없으면 새로 만든다.
2. 신솔라가 쓰는 잡 이름·주기·방식을 참고한다(잡 이름
   `solar-bible-tasks-poller`, 3분 주기, `tasks/pending/`을 보고 새
   파일이면 처리 후 `tasks/done/`으로 옮기고 원본 삭제 + git push까지
   하는 방식 — `tasks/done/2026-09-14-poller-fix.md`,
   `tasks/done/2026-09-14-autonomous-polling.md`에 신솔라가 어떻게
   설정했는지 적혀 있다, 참고만 하고 그대로 복붙하지 말고 이 PC 환경에
   맞게 확인해라).
3. 잡 프롬프트에 반드시 넣을 것:
   - 매 실행마다 `git pull`로 최신 상태부터 받는다.
   - `tasks/pending/`의 파일 중 **"받는 이: 구솔라"라고 적힌 것만**
     처리한다. "받는 이: 신솔라"인 파일은 절대 건드리지 않는다(솔라바이블
     §8 세팅 문서, "한 작업 파일은 한 에이전트만 쓴다").
   - 처리 후 `tasks/done/`으로 결과를 옮기되, **실제 조사·조치 내용을
     "조사 결과"/"처리 결과" 절에 채운 뒤에만** 옮긴다(오늘 있었던 사고:
     내용 없이 그냥 옮겨져 완료로 잘못 표시된 적이 두 번 있었다,
     `tasks/done/2026-09-15-auto-load-solarbible.md`의 "정정" 절 참고 —
     같은 실수를 반복하지 마라).
   - 옮긴 뒤 `tasks/pending/`의 원본은 반드시 삭제하고, git add·commit·
     push까지 한 사이클 안에 끝낸다.

## 완료 기준

잡을 만들었거나 수정한 내용(잡 이름, 주기, 프롬프트 핵심)을 이 파일에
적는다. **실제로 한 사이클 이상 기다려서(또는 `hermes cron tick`으로
강제 실행해) 이 PC 앞으로 온 대기 작업(예:
`tasks/pending/2026-09-15-gusolar-telegram-fix-최우선.md`)이 자동으로
처리되는지 실제 확인**하고, 그 결과(성공/실패)까지 적은 뒤에만
`tasks/done/2026-09-15-gusolar-setup-autopoll.md`로 옮기고 git add·
commit·push한다. "잡을 만들었다"만으로는 완료가 아니다 — 실제로 한 번
돌아가는 걸 봐야 한다(DONE=VERIFIED).
