# 대기 작업: LiteLLM 프록시 로그 분석 (읽기 전용)

받는 이: 신솔라
상태: QUEUED
우선순위: 7
발주: 탐(로컬), 사장님 승인 2026-09-19
읽는 방법: 이 파일 전체를 읽고 수행한다. 요약본만 보고 수행하지 않는다.

목표: LiteLLM 프록시가 왜 자꾸 죽는지 단서를 로그에서 뽑는다. 읽기 전용 분석이다.
대상 파일: C:\Users\PC\AppData\Local\hermes\litellm-proxy\proxy.log (읽기만, 수정 금지)

절차:
1. "Started server process" 줄마다 (줄 번호, 그 직전 로그 시각)을 표로 만든다. 재시작 횟수도 적는다.
2. 401 응답 줄을 모아 (시각, 메서드와 경로, 시간대별 횟수)를 표로 만든다.
   특히 POST /v1/chat/completions 401 이 언제 몇 번 있었는지 적는다.
3. 재시작마다 그 직전 30줄 안에서 종료 흔적(Shutting down, KeyboardInterrupt, ^C, SIGTERM,
   Traceback, Error, Killed, out of memory)이 있는 줄만 원문으로 발췌한다. 없으면 "종료 흔적 없음".
4. 재시작 각각에 대해 "종료 흔적 있음/없음"을 표로 정리하고, 원인 후보를 3줄 이내로 쓴다.
   추측은 [추정]으로 표시한다.

금지: 로그 전문을 붙이지 않는다(표와 발췌만). 키·토큰·Authorization 값이 보이면 <가림>으로 바꾼다.
로그를 수정·삭제·이동하지 않는다. LiteLLM을 재시작하지 않는다. 사용자 계정명은 <사용자>로 표기한다.

완료 기준: 표 3개(재시작, 401, 종료 흔적)와 원인 후보 3줄.

완료 보고 마지막에 증거 스냅샷을 붙인다:
  python C:\Users\PC\AppData\Local\hermes\scripts\evidence_snapshot.py C:\work\solar-bible

## 공통 규칙 (이 지시서 전체에 적용)

보고 서식 (이 순서를 지킬 것, 칸을 생략하지 말 것)
TASK: 무엇을 하라고 했는가 (한 줄)
EXECUTION: 실제로 실행한 명령
OBSERVATION: 명령이 실제로 출력한 결과 (요약하지 말고 핵심 줄 그대로)
VERIFICATION: 완료 기준 각각에 대해 통과/실패
STATUS: DONE / 실패 / 일부만 완료 (셋 중 하나만)

- 작업 위치: 지시서에 적힌 절대 경로에서만 작업한다. 작업 전에 그 경로에서
  git status -sb 원문을 붙인다. 새 클론을 만들지 않는다.
- "running", "실행 중", "예약됨"은 완료가 아니다. 결과 로그나 출력 원문이 있어야 DONE이다.
- 금지 표현: "적용 완료(변경 안 함)"처럼 뜻이 부딪히는 문장. 바꿨으면 "바꿈", 안 바꿨으면 "안 바꿈".
- 확인하지 못한 것은 "확인 못 함"으로 쓴다. 추측을 사실처럼 쓰지 않는다.
- 비밀값(API 키, 토큰, 비밀번호)은 출력·기록하지 않는다. 보고서에도 쓰지 않는다.
- 이 저장소(solar-bible)는 공개다. 보고서와 커밋에 호스트명, IP 주소, 사용자 계정명,
  개인 파일명을 쓰지 않는다. 필요하면 <호스트>, <사용자>, <IP>로 표기한다.
- 파일·폴더 삭제, 이동, 덮어쓰기 금지 (이 지시서가 명시한 것 제외).
  D 드라이브 안의 어떤 것도 지우거나 옮기지 않는다.
- 파일·폴더 경로는 지시서에 적힌 것만 쓴다. 큰 파일을 찾으려고 C:\ 같은 넓은 범위를
  재귀 스캔하지 않는다. 경로가 없으면 스캔하지 말고 "경로 없음"으로 보고하고 멈춘다.
- 출처를 적을 때는 실제로 읽은 파일 종류를 그대로 쓴다(추측으로 채우지 않는다).
- 최종 보고 원문은 화면에만 두지 말고 C:\work\solar-bible\tasks\done\ 의 이 지시서
  파일 아래에도 남긴다.
- 막히면 멈추고 막힌 이유를 보고한다. 우회하지 않는다.
- 15턴 안에 못 끝나면 "여기까지 했고 다음은 이것"을 보고하고 멈춘다.
