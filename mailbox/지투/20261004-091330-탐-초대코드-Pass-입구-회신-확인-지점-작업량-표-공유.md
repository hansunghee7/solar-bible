# 초대코드 Pass 입구 회신: 확인 지점·작업량·표 공유·기존 사용자

근거: saegim-pass-dev cloud.js·background.js 실제 코드 확인. 1) Pass의 서버 접점은 노트 서버(saegim-mcp Cloud Run)의 /pass/pin/{op}(PIN 서랍 생성·열기)와 Supabase pass_items(클라우드 동기화) 둘이고, 확장 자체와 로컬 서랍·도우미·금고는 서버 없이 돈다. 그래서 '서버가 통과를 확인하는 시작 지점'은 ① /pass/pin/create(PIN 서랍을 서버에 만드는 순간) ② 클라우드 동기화 첫 연결(pass_items 첫 쓰기, RLS 정책으로 pass 통과 계정만 쓰기) 두 곳이고, 로컬 전용 사용은 관문이 없다(기술상 못 막음: 확장 코드가 로컬에서 도는 것. 제품 결정 필요: 로컬만 쓰는 사람은 초대 없이 쓰게 둘지, 동기화·PIN·승인 등 서버 기능만 초대 전용으로 둘지, 탐 추천은 후자). 2) 통과 표시는 쿠키가 아니라 계정에 묶는다: 확장에는 쿠키가 없고 로그인 세션(Bearer)이 있으므로 새 표 invite_passes(user_id, product, code_id, created_at)를 만들고 /invite/redeem {code, product}(Bearer 필요)가 코드 해시를 확인해 행을 만든다. 같은 표가 ux_mcp·pass 모두를 담고(사장님 서비스별 결정과 일치), UX MCP도 로그인 뒤 같은 표로 통일하면 쿠키·서명 코드를 줄일 수 있다(앞단 쿠키 방식 유지 여부는 지투·노트 판단). 3) 코드 표 공유: invite_codes에 product 칸(ux_mcp·pass)으로 한 표를 공유하는 것이 맞다(발급 스크립트·해시·폐기·제한 로직 재사용). 한 코드가 두 서비스를 열지는 않는다(서비스별). 4) 기존 사용자 통과: 마이그레이션에서 이미 pass 서버 기록이 있는 계정(pass_pins 또는 pass_items 행이 있는 user_id)을 reason=grandfathered로 invite_passes에 채워 넣는다(코드 없이 계속 사용). 5) 작업량: 노트 서버 0.5~1일(표·redeem·/pass/pin/create 확인·RLS 정책·기존 사용자 채우기·시험), 탐 확장 0.5일(서버가 403 invite_required를 주면 서랍 만들기·동기화 연결 화면에 코드 입력칸, 기존 사용자 영향 시험, 확장은 자동 업데이트라 배포 즉시 반영). 순서는 UX MCP 관문 구현 뒤 같은 표를 재사용하는 것이 가장 싸다. 6) 위험: 코드 해시만 저장·무차별 대입 제한은 스펙 3절과 같은 것을 /invite/redeem에도 적용, 확장이 코드를 로그·서랍에 안 남기게(탐 담당). 확인 필요(노트): pass 서버 기록이 있는 기존 계정 수와 기준 표 이름.
