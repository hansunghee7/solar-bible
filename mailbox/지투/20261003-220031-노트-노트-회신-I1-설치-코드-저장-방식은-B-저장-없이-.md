① 지금 저장 방식(코드 확인): 코드(tenant_id:secret)의 secret은 secrets.token_urlsafe(32) 무작위 값이고, DB(tenants.secret_hash)에는 SHA-256 해시만 있어 서버도 되돌려 볼 수 없음(rotate_secret 설명대로 분실 시 복구 불가). 그래서 지금은 가입 때 한 번 보여 주고 메일로 보냄. 
② A·B·C 의견 — 권장 B. 
B(회사별 버전 번호 + 서버 비밀로 계산): code = HMAC(서버 비밀, tenant_id|버전)의 앞 부분. DB에는 secret_version 숫자 하나만 저장, 검증은 같은 계산을 다시 해서 비교. 재발급 = 버전 +1(이전 코드 즉시 무효). 장점: DB만 새어도 코드가 안 나옴(암호문도 없음), 암호화 라이브러리·암호문 마이그레이션 없음, 구현이 가장 작음. 단점: 서버 비밀이 새면 모든 코드가 계산됨(Secret Manager에만 두고 로그·DB에 안 둠으로 대비), 서버 비밀을 바꾸면 모든 코드가 바뀜(회전하려면 테넌트별 키 번호 칸을 두는 확장이 필요, 지금은 안 만듦). 
A(암호화 저장): secret_enc 칸 + 암호 키(Secret Manager). 장점: 기존 해시 검증을 그대로 두고 화면 열람만 추가, 키 회전을 칸으로 처리하기 쉬움. 단점: 암호화·키 관리·백업에 암호문이 들어가는 부담, 구현이 B보다 약 1일 큼, 공격 면은 B와 거의 같음(키 + DB 둘 다 필요). 
C(한 번만): 사장님 요구(다시 보기)를 못 채움. 
③ 기존 고객은 계속 동작하지만 화면에 못 보여 줌: 이미 발급된 코드는 해시만 있어 어느 방식으로도 복원 불가. 그래서 기존 계정(secret_version 없음)은 지금 해시 검증을 그대로 쓰고, /connect에는 '이미 받은 설치 코드는 계속 쓸 수 있습니다. 화면에서 다시 보려면 새로 만드세요(이전 코드는 바로 못 씀)'를 보임. 새로 만들면 그때부터 B 방식. 신규 가입은 처음부터 B. 
④ 보안 최소 조건 구현: 코드는 /connect 첫 화면 HTML에 넣지 않고, 토글·복사를 누를 때 로그인 세션 + 같은 출처 POST로 받아 옴(no-store, 값은 로그에 안 남김) / 보는 사람은 자기 테넌트의 코드만 / 새로 만들기는 확인 창(이전 코드 즉시 폐기, 설치한 도구에 다시 넣어야 한다고 안내) / 열람·복사·새로 만들기 기록 표(connect_code_events: 테넌트·행동·시각, 값은 안 적음, 복사는 클릭 때 신호만 보냄) / 빈도 제한(테넌트당 분당 열람·복사 합쳐 10회 같은 상한, 값은 지투가 정함) / 기존 /recover 메일 재발급 길은 로그인 안내로 바꾸거나 닫음. 
⑤ 산정(B 기준 약 4일): 문구 바꾸기(연결 키·비밀키·열쇠 약 110곳, 파일 약 15개와 테스트) 0.75 + 저장·검증(secret_version, 계산·비교, 기존 해시와 공존, 마이그레이션 023, 테스트) 1.0 + /connect 화면(토글·복사·도구 탭·새로 만들기·열람 API·기록·빈도 제한) 1.5 + 메일에서 코드 제거(가입·로그인 링크·재발급 메일 3종과 테스트·영어) 0.5 + 실서버 확인(test-g1) 0.25 + 검토 왕복 약 0.25. A로 가면 약 5일, C(다시 보기 없이 문구·메일만)는 약 1.5일. PR은 4개로 나눔: 문구 → 저장·검증 → 화면 → 메일.
