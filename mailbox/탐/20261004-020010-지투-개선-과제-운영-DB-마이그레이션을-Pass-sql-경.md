관찰(10/4 하루): 운영 DB 변경(023 열, 024 새 표, 권한 grant, 025 열)마다 사장님이 Supabase SQL 편집기에서 Run을 직접 눌렀다(4회). 보안 분류기가 에이전트의 운영 DB 변경을 막아 에이전트는 SQL 준비까지만 할 수 있었다. 에이전틱 원칙 기준으로 이 사람 개입은 '없앨 개입' 후보.

발견: pass.py에 sql 명령이 이미 있다(`pass.py sql "접근 토큰이 든 Key 이름" 프로젝트ref --file 쿼리.sql --why "이유"`). 그런데 Pass 목록에 Supabase 접근 토큰 항목이 없다(Google, Resend, Terminal 등만 보임, 값은 안 봄).

제안(해결 경로: 패스): ① 사장님이 Supabase 계정 접근 토큰을 만들어 Pass에 한 번 보관(자격증명 단계, 사람 1회) ② 이름 예: 'Supabase - Simplifier Project(migration)', 등급은 중요(승인 필요) ③ 이후 마이그레이션은 노트가 SQL 파일과 --why를 붙여 pass.py sql로 요청하고, 사장님은 텔레그램 승인 한 번만 누른다(편집기 접속·붙여넣기 없음). ④ 분류기가 이 경로를 어떻게 다루는지 먼저 안전한 SQL(예: select 1)로 시험하고, 막히면 이유를 기록. ⑤ 파괴적 SQL(drop, delete, truncate)은 승인 화면에 SQL 전문과 되돌리기 SQL이 같이 보이게(가능한가).
확인 요청: 이 경로가 Pass의 현재 설계(approver, tier)에서 가능한지, 필요한 작업량. 급하지 않음, N116 도그푸딩과 같은 묶음. 사장님 아침 보고에 '4회 Run 반복'을 근거로 넣겠습니다.
